## 一、系统概述

AI 测试平台是一个集成了项目管理、测试环境管理、知识库管理、功能测试、接口测试、测试执行和 AI 辅助测试等功能的综合性测试平台。该平台旨在提高测试效率，实现测试自动化，并通过 AI 技术辅助测试用例生成、预执行验证与正式执行。

## 二、系统架构

### 1、系统模块设计

1. 用户模块
2. 项目模块
3. 测试环境模块
4. **知识库管理模块**
5. 功能测试模块
6. 接口测试模块
7. 测试管理模块
8. 测试执行模块
9. AI 用例生成模块
10. WEB 测试模块（后续扩展）

### 2. 模块间交互关系

- 用户模块 → 项目模块：用户创建和管理项目
- 项目模块 → 测试环境模块：项目关联多个测试环境
- 项目模块 → **知识库管理模块**：项目关联独立 RAG workspace
- **知识库管理模块** → 功能测试模块 / 接口测试模块：提供需求与接口文档检索
- 项目模块 → 功能测试模块：项目包含多个需求和功能用例
- 项目模块 → 接口测试模块：项目包含多个接口和 API 用例
- 功能测试模块 → 测试管理模块：功能用例组织到测试套件
- 接口测试模块 → 测试管理模块：API 用例组织到测试套件
- 测试管理模块 → 测试执行模块：执行测试任务和套件
- 接口测试模块 / 功能测试模块 → AI 用例生成模块：基于文档生成用例
- AI 用例生成模块 → 接口测试模块 / 功能测试模块：生成结果入库

### 3. 用户角色与权限

- 超级管理员：系统全局管理权限
- 项目所有者：项目全部权限
- 项目编辑者：项目资源编辑权限
- 项目查看者：项目资源查看权限

### 3. 测试环境模块

#### 3.1 功能描述

#### 3.2 核心功能

- 测试环境配置管理（base_url、headers、envs）
- 环境变量目录（env_catalog）与变量文件（test_environment）

| environment_db_relation | 变量文件 ↔ DB 连接 M:N |
| env_function_file | 函数文件（file_name 全局唯一，source_code） |
| environment_function_relation | 变量文件 ↔ 函数文件 M:N（sort_order） |

| debug_runtime_var | 调试变量（source=manual \| engine） |
| test_environment_snapshot | 整包 payload JSON（version，is_active） |

**test_env_data 与表的映射**

| test_env_data 字段 | 存储位置 |
|--------------------|----------|
| base_url | test_environment_config（group=base） |

### 4. 知识库管理模块

#### 4.1 功能描述

按项目隔离管理需求文档与接口文档，为 RAG 检索和 AI 用例生成提供知识来源。

#### 4.2 核心功能

- 项目级知识库 workspace 管理（与 `rag/rag_storage/{project}/` 对应）
- 需求文档上传与索引（Markdown、PDF 等，经 LightRAG / RAGAnything 处理）
- 接口文档上传与索引（Swagger/OpenAPI JSON、Markdown 说明）
- 文档检索（功能需求检索、接口文档流式检索）
- 文档版本与重新索引

#### 4.3 实现方式

| 能力 | 实现 |
|------|------|
| 需求/接口 RAG | **RagGateway**：LightRAG 服务可用 → `RAGClient`；否则 → `RAGManager` |
| Agent 工具 | `search_requirement`、`search_api_document`（Phase D 改造） |
| 文档解析 | Swagger/OpenAPI → `utils/parser/`；AI → RAGAnything / LightRAG |

#### 4.4 数据模型

| 表名 | 职责 |
|------|------|
| knowledge_workspace | 项目级 RAG workspace（requirement / api） |
| knowledge_document | **逻辑文档**（title、project、doc_type、parse_mode 不可变） |
| knowledge_document_version | **版本记录**（文件、索引/解析状态、RAG doc id） |

**与业务表关系**

- 需求 AI 索引成功 → **upsert** `requirement_candidate`（用户 confirm 后写入 `requirement_doc`）
- 接口 Swagger/OpenAPI 解析 → 结果暂存 version；**手动** import 到 `api_interface.module_id`
- 删除知识库 → 不删除已 sync 的 requirement / api_interface（FK SET NULL）

**Phase 进度**

- Phase A：DB 迁移 + 项目 module CRUD + ORM（已完成）
- Phase B：知识库 CRUD / 分页 / 权限（已完成）
- Phase C：异步索引 + RagGateway（已完成）
- Phase D：import-interfaces + MCP 改造（已完成）

### 5. 功能测试模块

#### 5.1 功能描述

管理需求文档和功能测试用例，支持知识库索引候选确认、AI 辅助生成与纯手工维护。

#### 5.2 核心功能

- **需求管理**（两种方式）
  - 方式一：知识库 requirement 文档索引 → `requirement_candidate` 待确认 Tab → 用户 confirm → `requirement_doc`
  - 方式二：手工新增 `requirement_doc`（`source_type=manual`，module 必填）
- **待确认候选**：列表 / 数量 badge / 详情预览 / confirm（同版本 409）/ cancel
- **用例目录**：`functional_case_catalog` 三级树
- **功能用例**：纯手工新建、复制、排序、批量编辑/删除、CSV 导出
- **AI 生成**：会话预览 `output_payload` → 勾选保存 → `functional_test_point` + `functional_case`
- **测试点管理**（AI 中间产物，详情展示）
- 用例执行结果 `exec_result` 与套件删除 409 保护

#### 5.3 数据模型

- `requirement_candidate`（知识库索引产出，待用户确认）
- `requirement_doc`（含 `source_type`、同项目 title 唯一）
- `functional_case_catalog`
- `functional_test_point`
- `functional_case`（含 `catalog_id`、`sort_order`、`exec_result`、`jira_issue_key`）

**知识库 → 需求链路**

```
knowledge index → requirement_candidate → confirm API → requirement_doc
```

**AI 生成链路**

```
requirement_doc → ai_generation_session(output_payload) → functional_test_point → functional_case
```

### 7. 测试管理模块

#### 7.1 功能描述

组织和管理测试任务和测试套件，实现测试的系统化管理。

#### 7.2 核心功能

- 测试任务管理（含 project_id、module_id、environment_id、run_mode）
- 测试套件管理（含 project_id、module_id、environment_id、run_mode）
- API 套件关联 API 可执行用例（`suite_case_relation`，含 `use_dependency`）
- API/UI 任务关联同类型套件（`task_suite_relation`）
- 功能（手工）任务直挂功能用例（`task_case_relation`，不经套件）
- 列表最近执行态来自 last run 查询，不回写定义表 status

#### 7.3 数据模型

- test_task（type：api / functional / ui；functional 无 environment_id）
- test_suite（type：api / functional / ui；api 套件 environment_id 必填）
- **suite_case_relation**（case_type：api + case_id + case_order + use_dependency）
- **task_suite_relation**（api/ui 任务 → 套件）
- **task_case_relation**（functional 任务 → functional_case，case_order）

#### 7.4 API 路由（Phase C）

- 定义层：`/api/v1/test-management/suites|tasks|pickers|defects/...`
- 执行层：`/api/v1/test-execution/runs|defects/...`

#### 7.5 缺陷管理子模块

**功能描述**：统一管理测试缺陷（独立创建、执行报告关联、批量 external_key 关联），支持列表/搜索、编辑、状态流转、评论与历史审计。

**核心能力**

- 独立添加缺陷（`source_type=manual`）
- 执行报告单条关联创建（`POST /test-execution/defects`）
- 批量关联（`external_key` 或已有 `defect_id`）
- 列表/搜索（project_id 必填；标题、ID、严重程度、优先级、状态、类型、提交人、处理人、提交时间范围）
- 编辑（不含 status/assignee；可改项目，须双项目 editor 权限）
- 处理缺陷：五态流转 `init → open → in_progress → resolved → closed`（`closed` 可 reopen → `open`）
- 评论仅追加，不可改删；备注即首条/追加评论
- 详情：全字段 + 模块 + 关联 case/run + 评论 + 历史 + 状态时间线
- **不支持删除**

**缺陷类型（defect_category）**：功能 / 性能 / 界面 / 兼容 / 安全 / 其他；与 `source_type`（来源）分离。从功能用例创建时按 `functional_test_point.type` / `dimension` 预填。

**权限**：项目 viewer 只读；editor/owner 可写。分页统一 `Paginated[T]`，默认 20 条。

**API（缺陷管理）**

```plain
GET   /api/v1/test-management/defects
POST  /api/v1/test-management/defects
GET   /api/v1/test-management/defects/{id}
PATCH /api/v1/test-management/defects/{id}
POST  /api/v1/test-management/defects/{id}/transition
POST  /api/v1/test-management/defects/{id}/comments
POST  /api/v1/test-execution/defects
POST  /api/v1/test-execution/defects/batch-link
```

**代码分包**

- `service/test_management/defect/`：CRUD、transition、comment、category_mapper、history_writer
- `service/test_execution/defect/`：从 run 上下文创建/批量关联（委托 defect_writer）

### 8. 测试执行模块

#### 8.1 功能描述

执行测试用例，记录测试结果，生成测试报告。区分 **API 自动化执行** 与 **功能用例执行** 两种模式。

#### 8.2 核心功能

- **API 用例执行**（TestApiEngine）：单用例调试、套件执行、任务执行
- **功能用例执行**：当前以手工执行 + 结果回填为主；后续扩展 UI 自动化
- 执行结果记录（含环境快照、用例快照）
- 测试报告生成与查看

#### 8.3 API 自动化执行

**执行引擎**：TestApiEngine（`TestApiEngineXin/ApiEngine/core.py` → `TestRunner`）

**流程**

1. 从 test_task / test_suite 解析用例列表（suite_case_relation，case_type=api）
2. 加载 test_environment_snapshot.payload 作为 test_env_data
3. 从 api_test_case 读取 case_payload（exec_status=ready）
4. 调用 TestRunner.execute_cases()
5. 写入 api_case_run_record（含 case_snapshot、status、duration_ms、log_data）

**与 AI 预执行的区别**

| 项目 | AI 预执行 | 平台正式执行 |
|------|-----------|--------------|
| 触发 | api_runcase_workflow | test_execution 服务 |
| 目的 | 验证生成质量 | 回归/任务执行 |
| 状态字段 | review_status | exec_status + 运行记录 |
| 环境 | 当前 test_env_data | env_snapshot_id 固定快照 |

#### 8.4 功能用例执行

当前阶段（Phase C）：

- 功能任务（type=functional）通过 `task_case_relation` 直挂用例
- 执行会话：存在 running 的 `test_task_run` 则恢复，否则新建
- 测试人员查看 functional_case，手工执行后回填 `functional_case_run_record`
- 结果枚举：passed / failed / blocked / skipped（`FunctionalExecResult`）
- 可选关联 `test_defect`

#### 8.5 测试报告（最小设计）

**报告粒度**

| 级别 | 数据来源 | 内容 |
|------|----------|------|
| 用例级 | api_case_run_record | 单用例 status、请求/响应、日志、耗时 |
| 套件级 | test_suite_run | 通过/失败/异常/跳过统计、用例明细列表 |
| 任务级 | test_task_run | 多套件汇总、总通过率、执行时间线 |

**报告字段（任务级汇总示例）**

```json
{
  "task_run_id": 1,
  "task_name": "登录模块回归",
  "environment": "test",
  "start_time": "...",
  "duration_ms": 120000,
  "summary": {"total": 50, "passed": 45, "failed": 3, "error": 2, "skipped": 0},
  "pass_rate": 0.9,
  "suite_results": [...]
}
```

**API（Phase C）**

```plain
GET  /api/v1/test-execution/runs/suite-runs/{id}/report
GET  /api/v1/test-execution/runs/task-runs/{id}/report
GET  /api/v1/test-execution/runs/case-runs/{id}
POST /api/v1/test-execution/runs/suites/{suite_id}
POST /api/v1/test-execution/runs/tasks/{task_id}
POST /api/v1/test-execution/runs/tasks/{task_id}/manual
POST /api/v1/test-execution/runs/{run_id}/cancel
POST /api/v1/test-execution/defects
POST /api/v1/test-execution/defects/batch-link
```

（缺陷独立管理 API 见 §7.5。）

报告可由 task_run / suite_run / case_run 聚合生成，无需单独大表；可选增加 test_report 表存 PDF/HTML 导出快照。

#### 8.6 数据模型

- api_case_run_record（含 task_run_id、defect_id、status、environment_id、env_snapshot_id、case_snapshot、duration_ms、log_data）
- functional_case_run_record（task_run_id、functional_case_id、exec_result、remark、defect_id）
- test_defect（project_id、module_id、defect_category、title、steps、root_cause、severity、priority、status 五态、assignee_id、external_key、source_type、source_run_id、source_case_id、created_by_id、updated_at）
- test_defect_comment（defect_id、content、created_by_id、created_at）
- test_defect_history（defect_id、action、field_name、old_value、new_value、operator_id、created_at）
- test_suite_run（含 error_cases、skipped_cases、triggered_by、env_snapshot_id；status 含 cancelled）
- test_task_run（含 error_cases、skipped_cases、triggered_by、env_snapshot_id；status 含 cancelled）

### 9. AI 用例生成模块

#### 9.1 功能描述

利用 AI 技术，结合 RAG 知识库，根据需求文档和接口定义自动生成测试用例，并通过 TestApiEngine 预执行验证 API 用例可运行性。

#### 9.2 核心功能

- 基于需求文档生成功能测试点与功能用例
- 基于接口文档生成基础 API 用例与可执行结构化用例
- 覆盖率验证与测试点/用例补全
- **可执行用例预执行验证**（TestRunner）
- 失败自动重试（generation_count，上限 MAX_GENERATOR_COUNT）
- 用例审核（review_status → exec_status）
- 生成会话审计与追溯

#### 9.3 功能用例 AI 生成流程

```
1. 用户通过 Agent 或 API 发起请求（指定 project、module、需求描述）
2. search_requirement：RAG 检索需求文档
3. case_generator_workflow：
   a. 生成测试点 → 写入 functional_test_point（规划）
   b. 覆盖率验证 → 补全测试点
   c. 生成测试用例 → 写入 functional_case
4. 创建 ai_generation_session 记录（gen_type=functional）
5. 返回用例列表，source=ai
```

#### 9.4 API 用例 AI 生成流程

```
1. 用户选择目标接口或描述接口模块
2. search_api_document：RAG 检索接口文档
3. load_evn_data：加载 test_env_data（来自 test_environment_snapshot）
4. api_document_to_cases → APICaseGeneratorMainWorkflow：
   a. api_basecase_workflow：生成基础用例 → api_base_case
   b. api_runcase_workflow（并发）：基础用例 → 结构化可执行用例
   c. TestRunner 预执行 → review_status（success/fail/error）
   d. 失败则 re_structure_runcase_generator 重试（≤ MAX_GENERATOR_COUNT）
   e. 入库 api_test_case（case_payload + review_status + generation_count）
5. 创建 ai_generation_session 记录（gen_type=api_runnable）
6. 人工审核：review_status=success 且人工确认 → exec_status=ready
7. 加入 test_suite → 正式执行
```

#### 9.5 用例状态机

**API 可执行用例（api_test_case）**

| 字段 | 状态 | 含义 |
|------|------|------|
| review_status | init / success / fail / error | AI 预执行结果 |
| exec_status | pending / ready / disabled | 是否允许加入套件正式执行 |

状态流转：

```
生成 → review_status=init
     → 预执行 → success|fail|error
     → 人工审核通过 → exec_status=ready
     → 禁用 → exec_status=disabled
```

#### 9.6 数据模型

生成结果写入各用例表，审计信息写入 **ai_generation_session**（v2，详见 03 文档）：

- ai_generation_session（gen_type、input_ref、model_name、prompt_hash、status）
- functional_test_point.generation_session_id
- functional_case.generation_session_id
- api_base_case.generation_session_id
- api_test_case.generation_session_id

#### 9.8 智能体中心

**功能描述**

Phase 1 面向测试人员的统一 AI 用例生成入口，通过薄门面 [`service/ai_generation/`](../../ai_generation/) 复用现有 `GenerationService` 与 LangGraph workflow，**不新增数据库表**。推荐前端入口为 `/api/v1/ai-generation/*`；原有 `/api/v1/functional/case-generation/*` 与 `/api/v1/api-test/interfaces/{id}/cases/generate-*` 保留，权限行为与智能体对齐。

**前端入口**

- 侧栏菜单：**智能体中心**
- Tab 1：**手工用例智能体** — 基于需求描述或知识库文档生成功能用例预览
- Tab 2：**接口用例智能体** — 基于已有接口或粘贴接口文档生成 API 基础用例预览，confirm 后预执行落库
- 公共：`GET /meta` 返回 prompt 快捷模板、`single_interface_only: true`（Phase 1 单接口；多接口由前端循环调用）

**权限**

| 操作 | 权限 |
|------|------|
| 进入智能体中心、触发生成、轮询会话、编辑预览 | 登录 + 项目 **viewer** |
| 保存用例 / confirm 落库 | 项目 **editor** |
| 超级管理员 | 全项目 |

门面层 `ensure_agent_viewer` / `ensure_agent_editor` 委托项目成员权限；领域 `GenerationService` 内同步调整为 viewer 可生成/预览、editor 可保存/confirm。

**手工用例智能体 — 双输入路径**

| 路径 | 输入 | 说明 |
|------|------|------|
| (1) 需求描述 | `requirement_text` + 可选 `user_prompt` | 直接传入 workflow |
| (2) 知识库文档 | `knowledge_document_id` | 解析已索引需求文档全文写入 workflow（Phase 1 不走 RAG 检索）；与路径 (1) 二选一 |

- 预览区仍展示 workflow 产出的 `test_points + cases`；**保存时不写入 `requirement_doc` / `functional_test_point`**，仅将勾选 cases 落库至 `functional_case`（`requirement_id`、`test_point_id` 均为 NULL，`catalog_id` 必填）
- 知识库 picker 复用 `GET /api/v1/functional/requirements/candidates`（已索引候选列表）
- 自定义要求：`user_prompt` 注入各 workflow 节点 prompt，会话写入 `prompt_hash = sha256(源文本 + user_prompt)`

**接口用例智能体 — 双输入路径**

| 路径 | 输入 | 说明 |
|------|------|------|
| (1) 粘贴文档 | `api_doc_text` | `input_ref_type=api_doc`；workflow 调用时 **`precoditions=[]`**（无依赖上下文） |
| (2) 已有接口 | `interface_id` | 复用接口定义与依赖作为 preconditions |

- Phase 1 **单接口**；批量多接口由前端循环 `generate → confirm`，后端零改动
- 路径 (1) **confirm 时**解析文档创建 `api_interface`（`catalog_id` 来自 confirm 请求；同项目 method+path 已存在 → 409）；返回 `created_interface_id`
- 路径 (2) confirm 时 `interface_id` 必填
- 预执行失败仍入库，记录 `review_status` / 运行错误，无额外审核门禁

## 四、系统核心流程设计

### 1. 测试项目创建流程

1. 用户登录系统
2. 创建新项目，设置项目基本信息
3. 添加项目成员，分配权限
4. 创建项目模块
5. 配置测试环境（含 snapshot）
6. **上传需求/接口文档至知识库，完成 RAG 索引**

### 2. 功能测试用例流程

1. 创建或导入需求文档（requirement_doc + 知识库索引）
2. AI 或手工生成功能测试点（functional_test_point）
3. AI 或手工生成功能用例（functional_case）
4. 管理测试用例，加入测试套件
5. 手工执行并回填结果（或后续 UI 自动化）

### 3. 接口测试流程

1. 定义或导入接口信息（api_interface + 知识库索引）
2. 设置接口依赖关系（api_base_case.dependencies 或 api_dependency_group）
3. AI 生成 API 基础用例与可执行用例，TestApiEngine 预执行验证
4. 人工审核（exec_status=ready）
5. 组织 API 测试套件
6. 正式执行接口测试
7. 记录测试结果，生成报告

### 4. AI 辅助 API 测试用例生成流程

1. 选择目标接口（或自然语言描述）
2. RAG 检索接口文档，加载测试环境 snapshot
3. LangGraph 工作流：基础用例 → 可执行用例 → 预执行 → 重试
4. 写入 api_test_case，关联 ai_generation_session
5. 人工审核和优化（review_status / exec_status）
6. 将用例添加到测试套件
7. 执行测试并查看报告
