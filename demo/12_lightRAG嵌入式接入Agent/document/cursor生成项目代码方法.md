### 总体原则

要用 Cursor 帮你“从零写一个完整项目”，关键不是一句“大项目帮我写完”，而是**循序渐进 + 明确约束 + 小步闭环**。可以按下面的节奏来和我/Cursor 交互，会大幅提高成功率和整体质量。

---

### 1. 一开始就把“项目说明书”说清楚

第一次对话，尽量给出这些信息（可以分条发）：

- **目标**：项目要解决什么问题、面向谁，用起来是什么体验。
- **技术栈**：前后端语言、框架（如 Django + Vue3 + Element Plus）。
- **运行环境**：Windows / Linux、是否用 Docker、数据库选型（MySQL/PostgreSQL/SQLite）、是否有 Redis。
- **非功能需求**：权限/登录、国际化、多租户、并发量、是否考虑分布式、是否要 Celery 等。
- **时间/复杂度预期**：是 MVP 级别，还是要做到生产级。

建议你在第一条消息里就说类似：

> 我想做一个接口自动化平台，后端用 Django + Celery + MySQL，前端用 Vue3 + Element Plus，不用 Docker，部署目标是 xxx。帮我先做整体架构设计和目录结构规划，再分模块实现。

---

### 2. 先要“设计/规划”，再要“具体实现”

比较好的步骤是：

1. **先要一个整体方案**  
   让我先给出：
   
   - 目录结构（后端 apps/ 前端 views/components/stores）
   - 数据库模型草图
   - API 设计（路径、入参、出参）
- 前端路由和主要页面
  
2. **确认/修改方案**  
   你看方案不满意的地方，直接指出：“用例模型里还要加 X 字段”、“任务模块要多一个维度”等，我再改。

3. **再开始按模块实现**  
   比如顺序：
   - 用户 & 权限模块
   - 项目 & 环境模块
   - 接口 & 用例模块
   - 场景 & 任务 & 报告模块

   

   每个模块都：

   - 先给后端模型 & API
   - 再给前端页面 & 交互
   - 最后补测试 / 一键脚本 / 部署脚本

---

### 3. 用好“上下文 + 文件引用”

在 Cursor 里，你可以：

- 用 `@文件路径` 引用已有代码或配置，让我基于现有内容做增量修改，而不是凭空猜。
- 当你修改了一些东西，让我继续时，可以说：  
  “我刚改了 `src/api/index.js`，帮我检查 token 刷新和错误处理逻辑是否合理。”

这样我就能用 workspace 里的真实代码来推断，不会在脑补的代码上做设计。

---

### 4. 控制每次请求的“粒度”

避免两种极端：

- 极端 1：  
  “帮我写一个完整的 SaaS 接口自动化平台，前后端代码都生成，一次给我。”  
  → 太大，一次肯定不全面，bug 很多。
- 极端 2：  
  “帮我写一个 if 语句。”  
  → 粒度太小，沟通效率低。

比较合适的粒度示例：

- “在后端新增一个 `Project` 模块：模型 + serializer + viewset + url + 简单 API 文档。”
- “在前端增加 `项目列表` 页面：路由 + 页面布局 + 接口调用 + 分页。”
- “帮我加一个一键部署脚本（Windows + Linux 各一份），要求包含 venv/依赖安装/迁移/Celery 启动。”

---

### 5. 明确指出“可以改”和“不可以改”的地方

比如：

- “可以重构现有 `run_cases` 接口，但不要改现有数据库结构。”
- “可以调整前端路由守卫逻辑，但尽量不要动 `UserStore` 的 state 字段名。”
- “如果你需要新增依赖，请同时更新 `requirements.txt` / `package.json`。”

这样我会在给方案/写代码时遵守这些边界，减少和你现有逻辑冲突。

---

### 6. 把“可运行性”和“运维”也当成项目的一部分

从一开始就明确：

- 需要：
  - 一键部署脚本（Windows / Linux）
  - Dockerfile / docker-compose（如果用 Docker）
  - `requirements.txt` / `package.json` 保持同步
  - README：说明安装 / 运行 / 部署步骤
- 明确告诉我：  
  “请你在实现完主要功能后，顺带补上 README、部署脚本，并检查下 requirements / package.json 是否完整。”

---

### 7. 让 Cursor 帮你做“自检”

写完一个模块或改动后，可以要求：

- “帮我在后端跑一遍逻辑自查，看看有哪些明显的边界情况没考虑？”
- “从用户视角走一遍整个‘创建项目→配置环境→导入用例→运行→看报告’的流程，看还缺什么页面或按钮？”

我会基于已有代码和流程图帮你列出“待补充点”，然后我们再逐个补。

---

### 8. 多用“示例数据 / 使用场景”驱动设计

比如你这次给的 Postman 导入、`save_global_variable`、`调试运行变量`，就是非常好的“场景描述”。  
类似地，你可以多给：

- 一条典型用例 JSON
- 一条典型任务执行记录
- 用户真实操作路径（QA 同事是怎么用的）

这样我在设计模型、接口和前端交互时，会更贴近真实需求，而不是只按教科书结构来。

---

### 9. 不怕来回几轮

整体来说，可以按下面模式和我配合：

1. 你：给项目目标 + 技术栈 + 大概需求  
2. 我：给整体架构 / 数据模型 / API 设计  
3. 你：确认 + 小范围调整  
4. 我：分模块实现（你随时打断要求重构/补充，只要明确说）  
5. 你：运行 / 部署过程中遇到问题，贴命令 + 报错（就像你刚才做的那样）  
6. 我：根据真实报错/日志做修复 & 优化脚本

只要你愿意多提供**真实代码片段、错误信息、操作场景**，并让每次请求的目标尽量明确，Cursor 这边就能把“考虑全面、结构合理、成功率高”这几件事做得比较到位。





### 整体原则（一句话版）

- **Agent**：默认写代码、改代码、跑工具的工作模式。  
- **Plan**：在“先想清楚再写”时用，做架构/方案/拆任务。  
- **Debug**：有 bug / 报错 / 行为异常，需要系统排查时用。  
- **Ask**：只想“看代码、问问题、不改代码”时用。

---

### 1. Agent 模式（默认实现模式）

**适合阶段**

- 已经大致想好要做什么，开始真正“写代码 / 改代码 / 写脚本 / 改配置”的时候。
- 例如：
  - 实现某个接口、某个页面、某个脚本。
  - 写一键部署脚本、Dockerfile、docker-compose。
  - 按你确认过的方案重构某一块逻辑。

**特点**

- 可以读写代码、调用 Shell、改文件，是“真正动手干活”的模式。
- 大部分日常开发都在这个模式下完成。

---

### 2. Plan 模式（设计 / 拆解阶段）

**适合阶段**

- **项目刚开始**：要做整体架构设计、模块划分、数据模型设计。
  - 例如：你问“想用 Cursor 写一个完整项目，怎样结构更合理？”——就很适合先切到 Plan。
- **需求较大或有多种方案可选**：
  - 比如：选数据库方案、鉴权方案、部署方式（Docker vs 裸机 vs 混合）、如何集成 Celery/Redis 等。
- **你不确定应该怎么组织前后端结构**：
  - 比如让 Plan 给出：目录结构、apps 划分、路由/组件分层，再回到 Agent 实现。

**特点**

- **只读、不直接改代码**，专注于：
  - 方案对比
  - 架构设计
  - 任务拆解（生成 todo/里程碑）
- 用完 Plan 拿到一个你认可的“蓝图”之后，再切回 Agent 按图实作，成功率会更高。

---

### 3. Debug 模式（查 bug 阶段）

**适合阶段**

- 出现以下情况时：
  - 某个功能“报错 / 不工作 / 行为异常”；
  - 你有具体报错堆栈、日志、失败用例；
  - 自己尝试几次没定位出来原因。
- 典型例子：
  - `mysqlclient` 安装失败、Celery 不启动、接口返回 500；
  - 某个页面不显示“转 bug”按钮、token 刷新死循环等。

**特点**

- 更偏“系统化排查”：按现象 → 日志 → 代码路径一步步缩小范围。
- 一般流程：
  1. 你提供 **具体报错信息/截图/日志**（就像你发 mysqlclient、invalid syntax 等）。
  2. Debug 模式会建议如何复现、看哪几个文件、加什么日志、怎么改。
- 查完 / 修完 bug 后，再回到 Agent 延伸实现其他功能。

---

### 4. Ask 模式（纯阅读 / 咨询阶段）

**适合阶段**

- 你只想“看懂”和“问问题”，**暂时不希望改代码** 时：
  - 想搞清楚：
    - “这段代码做什么？”
    - “这个接口从前到后怎么走？”
    - “这个项目的大致结构是怎样的？”
  - 读别人项目，做 code review，做技术调研等。

**特点**

- 只读模式：不会动任何文件，也不会调用改写类的工具。
- 你可以反复问：“这个函数有哪些边界情况？”、“这块还有什么潜在 bug？”、“如何更优雅？”  
  适合你在正式动刀前，先把当前实现吃透。

---

### 建议的使用顺序（结合你这套平台）

1. **新功能 / 新项目开始**  
   - 切到 **Plan**：要整体架构、模块划分、数据模型、路由设计。  
   - 你确认方案后，切回 **Agent** 实现。

2. **具体模块开发 / 重构**  
   - 使用 **Agent**：实现接口、页面、部署脚本等。

3. **对已有代码不熟 / 想搞清楚行为**  
   - 切到 **Ask**：浏览文件，问“为什么要这样设计”、“这里是否有坑”。

4. **遇到 bug / 报错 / 行为异常**  
   - 切到 **Debug**：专门查问题；  
   - 修完后再用 **Agent** 做功能扩展。

只要在**大改动前先用 Plan 想清楚**，遇到问题时用 Debug 系统排查，日常实现用 Agent，阅读理解用 Ask，你和 Cursor 协作写完整项目时，成功率和整体质量都会明显更高。
