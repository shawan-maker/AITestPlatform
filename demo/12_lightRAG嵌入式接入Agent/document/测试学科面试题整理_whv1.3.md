#### 9，什么是关系型数据库，主键，外键，索引分别是什么？

关系型数据库是指：存储数据时有多个数据表格，表格之前有关联信息

常见的关系数据库有

- Oracle：在大型项目中使用，例如：银行、电信等项目 
- MySQL：Web 项目中使用最广泛的关系型数据库 
- Microsoft SQL Server：在微软的项目中使用 

主键为数据库表唯一标识，不能为空

外键：表与表之间关联的字段

索引：对数据库表中一列或多列的值进行排序的一种结构（相当于图书的目录)

- 作用：快速访问数据库表中的特定信息
- 索引的优势是：在表的数据量比较大时，查询的速度会大大加快
- 索引的逆势是：如果要进行表的修改操作时（增删改），由于要更新索引，修改速度会比没有索引时慢一些



#### 10，数据表的连接查询方式有哪些，有什么区别？（必会）

连接查询方式分为内连接及左连接和右连接

- 内连接：结果为两个表匹配到的数据
- 左连接：结果为两个表匹配到的数据加左表特有的数据，对于右表中不存在的数据使用null 填充
- 右连接：结果为两个表匹配到的数据加右表特有的数据，对于左表中不存在的数据使用null 填充

#### 5.你们公司的项目流程是怎么样的？你在项目组中承担了哪些工作？（必会）

1、接到项目之后，由项目经理、需求人员、测试经理和客户进行沟通，分析需求，需求人员编写需求文档，编写之后需求评审（看看有没有不能完成或者有必要增加或者修改的地方）。测试人员先读需求文档，记录需求中有疑问的地方，在需求评审会中提出；
2、评审过后，输出评审通过的需求规格说明书；开发人员根据需求说明书，设计说明进行软件开发。这时我们测试人员要了解客户需求，根据需求规格说明书编写测试用例，编写好之后对测试用例进行评审，在评审中注意有无遗漏或有误的地方，再进行修改。
3、测试用例评审通过，开发人员把项目写好，搭建好测试环境，我们首先进行冒烟测试，看看软件关键功能可不可以正常使用，环境通不通。然后我们根据测试用例进行测试，在测试过程中遇到bug，在缺陷管理工具中提交，并根据缺陷管理周期跟踪bug，复测通过之后关闭bug。
4、所有测试用例执行完毕，缺陷也关闭了，然后测试人员编写测试报告，完成后进入运行维护阶段。

- 举个例子来说，假设在tpshop上边购买了一件商品，但是在我的订单里面却没有记录，我会从这么几个步骤来进行分析：

  步骤：

  - 先查看数据库，检查商品是否下订单成功
    - 如果数据库中有对应的订单信息，说明查询我的订单存在问题
    - 如果数据库中没有对应的订单信息，说明下单的操作存在问题
  - 如果查询我的订单存在问题，使用fiddler抓取请求和响应的报文
    - 如果 查询我的订单的请求有问题（URL/参数不正确），说明是前端代码的问题
    - 如果 请求没有问题，但是响应有问题（无响应/响应结果错误），说明是后端代码的问题
    - 如果 请求和响应 都没有问题，需要具体分析。例如：浏览器兼容问题（前端问题）； 前后端开发人员对字段的定义不一致（status：1，后端开发人员认为表示成功，前端开发人员认为表示失败）
  - 如果下单的操作存在问题，使用fiddler抓取请求和响应的报文
    - 如果 下单的请求有问题，（URL/参数不正确），说明是前端代码的问题
    - 如果 请求没有问题，但是响应有问题（无响应/响应结果错误），说明是后端代码的问题
    - 如果 请求和响应 都没有问题，需要具体分析。例如：返回成功，但是使用insert语句在插入订单数据到数据库中，可能订单信息不满足订单表的字段类型/约束，导致插入数据失败（后端问题）

#### 22，APP冷启动和热启动有什么区别？  

冷启动：从离线状态，打开APP直到进入页面的过程。冷启动时会使用较多的流量及较多的请求，请求服务器的各种资源例如（图片，数据等）

热启动：从后台运行状态，打开APP直到进入页面的过程。热启动时则会在冷启动时从服务器获取的资源保存至本地，就不会再使用过多的流量及请求了，同时相比于冷启动流畅度会提升

#### 23，消息推送怎么测试？  

分为APP的服务器测试，手机端的测试，及app的状态的的测试

- 服务端测试为：推送的消息是否按照业务规则（例如：推送内容、推送时机、推送频率）推送的。当服务器设置推送特定人群时，接受此推送的是否符合特定人群

- 手机端测试：在手机设置不接受此APP的推送是否会接收到推送。根据服务器设置的推送消息显示位置，接收时是否一致。接收推送时，点击是否能跳转至此推送的详情或相关页面

- 根据app的状态进行测试：正在使用时收到推送如何显示。在后台时收到推送如何显示。退出后（离线）是否能收到推送。

#### 24，APP出现白屏或者闪退，一般是什么原因？你会如何分析问题？

​		APP闪退的原因很多，可能是：因为APP与手机系统版本不兼容，运行内存不足，CPU长时间使用率比较高，未连接网络，过低版本，手机内存不足、APP本身的bug（点两次银联支付出现空指针）等等

​		分析问题时，通常采取的方式有：（1）Fiddler抓包、（2）ADB查看APP日志 （3）GT/SoloPi监控手机资源使用情况、（4）查看服务器日志等方式。核心还是通过抓取报文和前后端的日志，确认APP客户端程序 和 服务器后端接口 的代码处理是否有错误，日志可以查看一些错误日志信息:如Error级别的、EXCEPTION异常的。如获取到类似日志我自己会做一些简单的分析，1是确认功能接口信息，2是识别常见的异常:如数组越界和空指针等问题。如分析不出来，则会提交日志信息给开发进行确认，同时也会咨询开发具体问题，累积经验。

#### 28，怎么抓取HTTPS的包？（必会）

一般抓包工具最常见的分为两种，一种为Fiddler ,一种为Charles，两者没有本质区别，区别在于Fiddler不能抓取mac操作系统，而Charles则没有限制，我就以Charles工具讲解

PC端web——

1、打开Charles工具找到help至SSL代理选择安装Charles证书，安装时将证书储存在”收信任的根证书颁发机构“，

2、安装完成后找到代理选择SSL代理设置，打开代理设置后勾选SSL代理开关并添加对应的https域名或者*，这样则成功抓取https包

移动端app——

1、首先确定电脑和手机是否在同一个局域网，例如同一个WIFI。

2、确定在同一个局域网后，在电脑上利用Charles工具设置端口（该端口未被占用，或者使用默认端口），然后在手机上设置WiFi代理，代理改成手动，IP改为电脑的IP，端口为Charles工具设置的端口，设置完成后会弹窗，点击Allow。

3、能确保能正常抓取http报文后分别在手机上安装证书。

- 在Charles工具上找到SSL代理，选择在移动设备上安装证书，操作完成后会弹窗，
- 此时在手机浏览器输入网址下载证书，
- 并将证书添加到信任列表中，
- 电脑Charles页面弹出信息，点击确定后。这样则就能在手机上成功抓取https包

#### 33，开发人员说你发现的bug不是bug时，你如何处理（必会）

2. 其次确认开发环境与测试环境是否一致，找出不一致的点，修改为一致再复现
3. 确认是否是偶现的难以复现的BUG，如何处理。。。。。

#### 34，测出一个bug,但是开发无法复现,你也无法复现,你该怎么办？（必会）

1. ⾸先，在遇到⾮必然重现的bug，⼀定要提bug，并且要在bug单中说明复现的概率。
2. 在发现bug时，要分析产⽣的原因，尽量多尝试可能出现的步骤。排除环境和⾃⼰电脑配置的原因，⽐如浏览器的版本，系统的版本，等。还可以寻找开发帮助，让开发同学对相应地⽅的代码进⾏检查，看⼀下是否可以通过代码层⾯检查出问题。
3. 如果还未复现，在接下来的测试中，时刻保持关注，每次执⾏同样或者相近的步骤的时候，看下是否能够复现之前的bug。
4. 那些⼀直未能复现的bug，需要测试经理定期将这些bug汇总，选择优先级⾼的缺陷，组织开发⼈员和测试⼈员专门投⼊到复现问题。
5. 如果经过这样的专门复现依然不能复现，可以降低问题的优先级。如果在项⽬前期，跟踪⾄少3个版本（每个版本如果没有复现该bug，则对bug进行降级，直到关闭），如果仍然⽆复现，可以暂时关闭该bug，备注说明并不是因为修复关闭，⽽是经过x个版本后不复现了。
6. 如果项⽬周期⽐较紧张，不能跟踪多个版本，那么bug就不能关闭，上线后及时关注⽤户的使⽤反馈，如果持续3或者4个版本没有出现（每个版本如果没有复现该bug，则对bug进行降级，直到关闭），那么可以将bug暂时关掉了，同时关掉的时候要进⾏备注说明。

#### 35，生产环境/用户线上环境出Bug了，你应该怎么办？（必会）

1，首先在公司的缺陷管理系统（如：禅道）中记录该缺陷及bug等级，并提供必要的截图和日志log信息(tail -200f log.txt)

2，随后找到bug信息定位（前端bug还是后端bug，sql问题？）—— 缩小问题的范围

3，确定bug的影响范围（严重程度）

- 如果严重程度很高，
  - 能复现：召集开发、产品、运维预估 bug 解决时间，当天（第二天）解决，并发布新版本
  - 不能复现/解决时间过长：可能是版本升级导致的，（联系运维、产品）是否需要需要回退到上一个安全稳定的版本

- 如果严重程度不高：
  - 能复现：召集开发、产品、运维预估 bug 解决时间，后续版本（下一个迭代）发布
  - 不能复现：正常跟踪随机bug的解决

4，bug 分析总结

- **测试不到位（更新测试用例）**
- 需求紧急变更（争取测试资源包含测试时间）
- 生产环境软硬件差异性（增加线上回归测试用例）

#### 36，你写过测试报告吗？测试报告都有哪些内容？测试报告有什么作用？

#### 3、http和https的区别		

- HTTP协议 是超⽂本传输协议，被⽤于在Web浏览器和⽹站服务器之间传递信息。 HTTP协议以明⽂⽅式发送内容，不提供任何⽅式的数据加密，如果攻击者截取了Web浏览器和⽹站服务器之 间的传输报⽂，就可以直接读懂其中的信息，因此HTTP协议不适合传输⼀些敏感信息，⽐如信⽤卡号、密码 等。
-  HTTPS（安全套接字层）传输协议,为了数据传输的安全，HTTPS在HTTP的基础上加⼊了SSL协议，SSL依靠证 书来验证服务器的身份，并为浏览器和服务器之间的通信加密。 
- 区别:
  - HTTP 的URL 以http:// 开头，⽽HTTPS 的URL 以https:// 开头 
  - HTTP 是不安全的明⽂传输，⽽ HTTPS 是安全的加密传输 
  - HTTP 标准端⼝是80 ，⽽ HTTPS 的标准端⼝是443 
  - 在OSI ⽹络模型中，HTTP⼯作于应⽤层，⽽HTTPS ⼯作在传输层 
  - HTTP ⽆法验证身份，⽽依赖于SSL证书的HTTPS 可验证服务器身份 
  - HTTP⽆需证书，⽽HTTPS 需要正规CA wosign 颁发的SSL证书 
  - HTTP协议：免费申请,⽽HTTPS协议：需要到ca申请证书，⼀般免费证书很少，需要交费					

#### 4、GET和POST的区别		

~~~
1.传递参数位置不同
 GET请求传递的参数放在URL中，所有⼈可⻅
 POST请求通过request body传递参数，不会显示在URL中
2.请求参数⻓度限制
 GET请求传递的参数⻓度有限制(不超过2048个字符)
 POST请求传递参数的⻓度⽆限制
3.请求参数的安全性
 GET请求安全性⽐较差不建议发送敏感数据，浏览器缓存能保存历史记录
 POST请求安全性较好，参数不会被保存到URL，浏览器缓存不会保存历史记录
4.请求数据类型的限制
 GET请求只允许ASCII码
 POST请求没有限制
5.请求是否可收藏
 GET请求可收藏为书签
 POST请求不可收藏为书签
6.浏览器回退/刷新
 GET请求对浏览器刷新或回退是⽆害的
 POST请求对浏览器回退/刷新是需要重新提交的			
~~~

```
如何调用微信或者支付宝的第三方接口：

我们需要对接五个接口

- 首先 商户客户端 发起支付，服务器返回签名后的订单信息，商户客户端再跳转到 第三方网站/APP 进行支付时，第三方支付公司用来校验是否合法的支付请求

- 退款，商户用该接口进行退款
- 退款查询，商户用该接口来判断退款结果成功与否
- 获取支付成功订单列表接口，获取第三方某日所有成功的支付订单列表，用于对账时使用

四个流程：

1. 发起支付请求
- 支付网关（服务器内部抽离的子系统）：我们将支付抽离为一个单独的系统，该系统用来对接所有支付

 首先 是：

发起支付（客户）- 请求支付网关（服务器）- 获取支付token（服务器）- 返回token（支付网关）-返回支付必须参数 （电商系统）-跳转到第三方支付页面（第三方支付）

签名校验：请求支付接口域名为内网域名，使用签名校验，让系统更加安全

记录请求日志：请求除了记录到log文件中，建议落库，方便日后查找

非首次支付判断支付状态：防止重复支付，该判断可在流量高峰期降配掉

生成新的支付号：部分第三方支付公司，规定同一个支付号，无论支付成功与否只能使用一次。目前，在小米网，当订单创建成功后，订单号不会改变，所以每次用户发起支付后，支付网关会生成新的支付号，使用该支付号请求第三方。该方案会引入重复支付问题，

2. 同步回调和异步回调

支付后，第三方支付会通知支付网关，支付结果。通知的实现一般会有两种方案

- 同步回调：支付后，立即回调支付网关提供的回调接口。该接口url一般在发起支付时，作为参数传递给第三方

- 异步回调：支付后，第三方支付会调用对接方提供的API，该API一般是对接的时候提供给第三方，第三方配置在自己系统中的。异步回调有重试机制，如果对接方没有返回指定结果，如httpcode不为200，则会在一段时间后重试，直到达到指定重试上线后，会停止重试

日志：传入和返回数据都做记录

签名校验：校验第三方签名十分重要，这是防止他人攻击的方案之一

判断支付成功：情况允许条件下，建议请求第三方查询接口来判断是否支付成功，这是防止他人攻击的方案之二

**跳转支付成功/失败页面：当发起支付时，支付成功或者失败页面的url会传给支付网关。之所以请求支付时传递该url，原因在于不同终端，url不同。**

该流程需要两个定时脚本进行支撑

**通知订单中心支付完成。因为更改支付系统的订单状态和通知订单中心未必会同时成功。**

**重复支付订单自动退款**

3.退款

退款整体流程一般为，财务系统向支付网关发起退款请求，支付网关将退款记录到表。支付系统定时进行退款，财务系统定时查询退款状态。

- 退款类型：退款一般分为两种类型

- 部分退款：有的第三方公司不支持，需要提前咨询

- 全额退款

待退款列表：建议同一个订单的多个退款单，确认处理完一个之后，再处理另一个

退款相关状态：调用第三方接口状态callStatus，退款结果状态refundStatus。callStatus成功，refundStatus未成功，可定时查退款状态

查询退款结果：可选，根据第三方API情况做判断

日志：请求日志和返回日志都进行记录

4.对账

对账的完成，需要第三方提供前一天的支付成功数据，然后和支付网关系统中当天的支付成功数据进行对比。

对不上账的类型有：

支付网关有数据，第三方没有数据：

- 可能被黑客攻击了，用户没有真正支付，但是我们发货了

- 代码有问题，用户没有完成支付，但是系统认为支付成功了

第三方提供数据不全：

- 支付网关没有数据，第三方有数据

- 用户支付成功，但是同步或者异步通知都失败了

- 金额不一致

- 代码有问题，电商发起支付金额和真正调用第三方金额不一致

- 第三方提供数据有问题

对账是验证支付系统准确的重要一环，可以帮助开发人员今早发现很多问题，建议每一种支付方式都要支持，并且及时对账
```

#### 20、**如何挑选自动化用例（谈谈你对自动化的理解）（必会）**

~~~
自动化其实就是用写代码的形式，代替我们手工的操作。

我们接口自动化一般都是在接口测试用例完成之后写，我们会从之前的接口测试的用例中挑一部分，大概占个百分之五六十吧，自动化脚本数量大概在200条左右。

这百分之五六十的挑选依据，主要是两个点。一个是主线业务，一个是需求不变。
 - 先来说主线业务，包括业务流程用例 + 单接口的测试用例（单接口测试用例用例优先测试正向的，有时间再测试逆向的）。
 - 还有就是刚才提到的需求不变。如果我们一个需求还不能够完全确定的情况写，比如再开会讨论的时候，这个功能现在是测试版，后期一定会修改，那这个功能就算是再主线的业务，我们也不会做自动化。因为一旦需求变了我们的代码肯定也会跟着变。

自动化测试的本质其实就是用一段代码来测试另外一段代码。

自动化一般在版本迭代或回归测试的时候使用。

其实自动化更多的时候不是为了找bug，而是为了确定一些之前的功能不会出现新的bug。

比如，我给您举个例子。我们现有一个1.0版本的应用，有5个功能。半个月之后又除了1.1的版本又在之前1.0的5个功能的基础上增加了10个功能。那么在1.1的这个测试期间中，我们肯定也需要花时间去测之前1.0的5个功能，（为了测试功能间有没有业务耦合产生的bug）。如果我之前对这5个功能写过自动化脚本。其实我只需要在这个时候跑一遍就行了，如果自动化的报告没有问题的话，那么基本可以确定之前的功能是没问题的。我也可以将更多的精力放新的十个功能写测试用例或功能测试上。

##### 24、常见的响应状态码有哪些？分别表示什么含义？

```python
2开头：2xx (成功)表示成功处理了请求的状态代码；如：200 (成功) 服务器已成功处理了请求。
3开头：3xx (重定向) 表示要完成请求，需要进一步操作。 通常，这些状态代码用来重定向。如：302表示请求URL错误，会返回正确的URL地址，由浏览器重新发送请求。
4开头：4xx(请求错误) 这些状态代码表示请求可能出错，妨碍了服务器的处理；如：400 (错误请求) 服务器不理解请求的语法；403 (禁止) 服务器拒绝请求。404 (未找到) 服务器找不到请求的网页。
5开头：5xx(服务器错误)这些状态代码表示服务器在尝试处理请求时发生内部错误。 这些错误可能是服务器本身的错误，而不是请求出错；如：500 (服务器内部错误) 服务器遇到错误，无法完成请求。
```

##### 28、cookie、token和session有什么区别，简答说下看看？

```python
session 是基于 cookie 实现的，session 存储在服务器端，sessionId 会被存储到客户端的cookie 中。
session 认证流程：
- 用户第一次请求服务器的时候，服务器根据用户提交的相关信息，创建对应的 Session
请求返回时将此 Session 的唯一标识信息 SessionID 返回给浏览器
浏览器接收到服务器返回的 SessionID 信息后，会将此信息存入到 Cookie 中，同时 Cookie 记录此 SessionID 属于哪个域名
- 当用户第二次访问服务器的时候，请求会自动判断此域名下是否存在 Cookie 信息，如果存在自动将 Cookie 信息也发送给服务端，服务端会从 Cookie 中获取 SessionID，再根据 SessionID 查找对应的 Session 信息，如果没有找到说明用户没有登录或者登录失效，如果找到 Session 证明用户已经登录可执行后面操作。

Token 认证流程：
Token是服务端生成的一串字符串，以作客户端进行请求的一个令牌，当第一次登录后，服务器生成一个Token便将此Token返回给客户端，以后客户端只需带上这个Token前来请求数据即可，无需再次带上用户名和密码。最简单的token组成:uid(用户唯一的身份标识)、time(当前时间的时间戳)、sign(签名，由token的前几位+盐以哈希算法压缩成一定长的十六进制字符串，可以防止恶意第三方拼接token请求服务器)。
```

##### 29、unittest 单元测试框和 pytest 测试框架有什么区别？

```
	unittest和pytest都是做单元测试的工具，其核心的思路是主体结构都是一样的。
	区别主要有如下几点：
	（1）unittest 是 python 自带的单元测试框架，pytest 是第三方单元测试框架，需要手动安装
	（2）pytest 执行顺序默认是从上往下执行，而 unittest 是通过用例名称的 assic 码字符值的大小来执行。
	（3）unittest 需要通过 suite 来定义测试集，而 pytest 不需要定位测试集，而是通过配置文件来确定要执行的用例。
	（4）pytest 可以执行 unittest 的用例，但是 unittest 不能支持 pytest 的用例
	（5）pytest 的类名和方法名可以自定义，但是 unittest 不行，类名和方法名的格式固定
```

#### 11、简单的说下PO模式的设计思想？（必会）

```python
	所谓的PO吧，就是Page Object页面对象,利用面向对象的思维来封装我们的UI自动化测试用例。
    使用这个框架的原因是:原元素定位的代码写在单元测试框架中,如登录的场景每次都要写几行元素定位和操作的代码，我们所要测试的场景很多都要登录，那每个测试用例都需要写这几行,如某天前端开发修改了其中的一个定位信息，那所有用到该定位的代码都需要进行修改。不方便维护了。
	而PO模式就是把我们测试过程中每个页面都当做对象,在我们的UI自动化测试框架中,每个页面都有一个独立的封装py文件,分为三层来管理:
    第一层是对象库层，将测试用例在该页面所有用到的元素对象统一找到并进行管理,
    第二层操作(方法)层:基于每个元素定义好其对应的操作方法,
    第三层:业务层,组装多个操作方法即可形成完整的业务操作。
    例如:登录页面:对象库层找到用户名、密码等元素，操作层封装用户名输入、密码输入等方法，业务层连续调用操作层方法，那调用业务层的登录方法传递输入参数即可完成登录。这样无论哪个测试用例需要进行登录都只需要调用该页面py文件业务层的登录方法即可完成登录了。这样整个UI自动化测试代码中,对应的元素定位代码只会存在一份了，方便了维护，也减少了代码的冗余。
```

#### 12、appium 的执行机制、原理是什么？

~~~
	Appium 启动时会创建一个 http://127.0.0.1:4723/wd/hub 服务端（相当于一个 中转站），脚本会告诉服务器我要做什么，服务端再去跟设备打交道。 
	服务端和设备默认使用 4724 端口进行通信的，底层调用 uiautoamato 工具，在测试 的时候服务端给设备扔一个 bootstrap.jar，会启动这个包，启动之后会在手机上创建一个 socket 服务，暴露的就是 4724 端口；相对 socket 服 务来说，appium 服务端又是一个 客户端； 
	服务端收到脚本传递过来的命令之后，通过电脑上的 4724 端口，向设备的 4724 端 口发送指令，bootstrap.jar 收到指令后会去完成点击，滑动等操作，完成之后再给服务端 一个响应。服务端收到之后再去运行脚本。
	appium 的加载过程：
	1）调用 Android adb 完成基本的系统操作 
	2）向 Android 上部署 bootstrap.jar 
	3）bootstrap.jar Forward Android 的端口到 PC 机器上
	4）PC 上监听端口接收请求，使用 webdriver 协议 
	5）分析命令并通过 forward 端口发给 bootstrap.jar 
	6）bootstrap.jar 接收请求并把命令发给 uiautomator 
	7）ui automator 执行命令
~~~

#### 5、压力测试、负载测试、并发测试有什么区别？

```python
	负载测试：目标是测试在一定负载情况下系统性能（不关注稳定性，也就是说不关注长时间运行，只是得到不同负载下相关性能指标即可）；实际中我们常从比较小的负载开始，逐渐增加模拟用户的数量（增加负载）， 观察不同负载下应用程序响应时间、所耗资源，直到超时或关键资源耗尽，这就是所说的负载测试，它是测试系统的不同负载情况下的性能指标。
    压力测试：压力测试的目标是测试系统在极端情况下的容错能力和错误的恢复能力。包括高负载下的稳定性压力测试（在高的负载下系统长时间运行的稳定性，尤其关注大业务量情况下长时间运行系统性能的变化）和极限负载下的破坏性压力测试（在超出系统的负载极限时，观察系统是否会崩溃，能否修复），同时观察系统是否反应变慢、是否会内存泄漏导致系统逐渐崩溃、是否能恢复；
	并发测试：主要指当测试多用户并发访问同一个应用、模块、数据时是否产生隐藏的并发问题，如内存泄漏、线程锁、资源争用问题，几乎所有的性能测试都会涉及并发测试。
```

#### 1、游戏测试与软件测试的区别

~~~
一、工作内容不同
游戏测试就是不断的玩游戏发现游戏中的bug。
软件测试就是不断的使专用软件发现软件中的bug。
二、要求不同
游戏测试：合格的游戏测试要具备企划游戏或者编写程序的能力，而且必须有相当的耐心与细心进行测试。
软件测试：及时发现软件问题并及时督促更正，确保产品的正常运作。
三、侧重点不同
软件测试：传统软件重点是在功能方面。
游戏测试：游戏的侧重点在体验方面。
四、交互点不同
游戏测试：交互的点会更多一些，每个人的动作不一样，操作不一样，玩家与玩家之间的交互，不纯是聊天，技能上交互
软件测试：正常流程，基础的异常，与其他软件的交互，比如微信分享
~~~



#### 2、游戏测试怎么测？

~~~
1、功能方面：
对于需求实明确要求实现的功能来说，软件测试和游戏测试是等同重要的；但是对于其中一些功能细节，可能游戏比软件要求要严格很多。

因为游戏而言，无论是单机游戏还是网络游戏，玩家非常重视自己角色的数值增长，这也是游戏之所以吸引用户的一种重要因素，因为用户可以在虚拟世界里找到自己的另一种价值；所以他的数据的精确就要求非常高了，因为非常细微的差别，就有可能会操作游戏排位的差别，从而造成用户的投诉以及流失；

而且软件的用户很多时候达到自己的功能需求就可以了，细微的差错可能都没人关心。

举个例子，比如很多电脑管家软件，在用户打开电脑时会提示用户开机速度击败了百分之多少的其它用户，本次是 20% 下次是 70%，大部分用户是不太在意的，只要电脑能正常打开并正常使用就可以；而游戏则不然，如果一个英雄角色的战斗力本次是 2000，下次登陆变成 1999，仅仅是 1 的差距，用户可能就会愤怒的打客服电话投诉了，甚至直接卸载软件，并给差评。

所以就功能测试而言，游戏测试精度要更准确一点。

2、界面测试：
对大部分软件来说，界面测试其实就是关注产品的界面设计是否符合需求文档和 UI 切图，在功能已经实现的基础上，界面似乎要求并没有那么严格，只要看起来是否符合大部分用户的常规审美即可；

而游戏则不然，在玩游戏的过程中，界面带来的视觉愉悦感和趣味性是至关重要的，很多用户喜欢玩一款游戏就是因为页面做得特别漂亮，或者炫酷；所以如果游戏缺失了这个要素，用户可能瞬间就流失了，也就意味着这款游戏失败了。

3、兼容性测试：
虽然对于软件和游戏我们都希望更多的用户能使用，这个目的是一致的。但是相对于软件来说，游戏对个别用户的兼容性要求更高；越是希望越多用户都能玩我们的游戏，那么用户的设备则差异性就越大，尤其是移动设备。所以我们必须确保游戏能够兼容更多的设备，那么就有更多的玩家能够玩我们的游戏，从而提高游戏的流传度。这样游戏公司才能盈利并存活下去。

4、性能测试：
软件虽然对性能也有要求，但是大部分小软件或者用户量没那么大的软件，并没有性能测试的需求，只要保证功能正常就可以；而且对于有大量用户的软件，更多的是关注大量用户并发的时候，软件的稳定性和健壮性，保证极端情况的正常运行；

而对于游戏而言，使用的流畅度是至关重要的一点。所以不仅是大量用户同时使用，还是单个用户的使用，游戏卡顿都会让用户产生厌恶感。而这种流畅度就体现在游戏的性能上。不管是对客户端的性能要求，还是服务端的性能要求都比较高。

5、安全测试
安全测试对软件和游戏而言都十分重要，不过两者的关注点不太一样。软件更加关注的是软件有无漏洞，这些漏洞如果留下会不会造成用户的私密信息泄露，或者财产安全；

而对于游戏而言，需要关注的一个重要的安全指标就是“外挂”，很多游戏都死于外挂横行，所以这点的安全测试是关乎游戏身家性命的事情。而且游戏的客户端与服务端的交互非常频繁，数据安全更加凸显。防刷防外挂，是游戏测试人员始终要保持谨慎认真对待的事情。

6、易用性测试
对于易用性这点，两者差别不是特别大，都是希望用户使用起来体验非常愉快，操作非常顺畅。唯一有点以不同的是，软件是希望用户操作越简单越好；而游戏却会按照由简及难的原则设置不同的关卡，越后面的关卡需要设置巧妙的难度，这样才算是满足的玩家用户的体验。

7、网络测试：
最后再补充一点网络测试的区别，游戏对于网络的要求一般比软件要更高一点，因为游戏的实时交互性比较高，游戏过程中突然断网或者弱网是难以忍受的。所以各种网络类型的覆盖，以及弱网环境的覆盖等，都是需要更深度的测试。这样才能尽量保证不同网络条件下用户的体验达到最佳。
~~~

### 八、数据库

#### 1、数据库重点知识

##### 1.1 查询的语法结构

~~~
select * from 表名 where 条件 group by 分组 having 条件 order by 顺序。
注意：WHERE，GROUP BY，HAVING，ORDER BY 顺序。
执⾏步骤：
1. 先从 from 字句⼀个表或多个表创建⼯作表
2. 将 where 条件应⽤于 源⼯作表，保留满⾜条件的⾏
3. group by 将 where过滤 的结果分成多个组
4. having 将条件应⽤于 分组后 的条件过滤，只保留符合要求的组
5. order by 对结果进⾏排序
~~~

##### 1.2 增删改的语法结构

~~~sql
# 增加数据
说明：主键⾃增⻓，可以⽤0或null代替。
⽅式⼀: insert into 表名 values(…)
例: insert into students values(0, '亚瑟', 22, 177.56)
⽅式⼆: inert into 表名 (字段1, 字段2, …) value(值1, 值2, …)
例: inert into students (name) values ('⽼夫⼦')
# 删除数据
delete from 表名 where 条件
例: 删除id为6的学⽣数据
delete from students where id=6
# 其他删除⽅法
truncate 删除数据:
truncate table 表名
例:删除学⽣表的所有数据(保留表结构)
truncate table students
drop 删除表:
drop table 表名
例: 删除学⽣表(包括所有数据和表结构)
drop table students
# 修改数据
update 表名 set 字段名1=值1,字段名2=值2... where 条件
例: 修改id为5的学⽣数据，姓名改为 狄仁杰，年龄改为 20
~~~

#####  1.3 SQL 条件查询、去重、排序、分组、分⻚、聚合函数

~~~sql
条件查询:

去重:
select distinct 字段1,... from 表名
~~~

##### 输入一行字符，分别统计出其中的英文字母、空格、数字和其他字符的个数

```python
#输入一行字符，分别统计出其中的英文字母、空格、数字和其他字符的个数，并用字典表示

a = {}
line = input('请输入一个字符串:')
for s in line:
    #判定是否为字母
    if s.isalpha():
        a['letters'] = a.setdefault('letters',0)+1
    # 判定是否为空格
    elif s.isspace():
        a['space'] = a.setdefault('space',0)+1
    # 判定是否为数字
    elif s.isdigit():
        a['digit'] = a.setdefault('digit',0)+1
    # 其他字符
    else:
        a['other'] = a.setdefault('other', 0) + 1
print("[%s]中字母个数=%d,数字个数=%d,空格个数=%d,其他字符个数=%d" % (line,a.get('letters'),a.get('digit'),a.get('space'),a.get('other')))
```

#### 8、寄快递的功能怎么测试？

填写的信息包括：收件人的**地址**/姓名/手机号，寄件人的**地址/**姓名/手机号/身份证号，**物品类型**，**重量**，**体积**，**是否保价**，**运输方式**，**付款方式**，输出（结果）的是费用

测试点：

- 地址相关：
  - 同城寄送（寄送成功）
  - 省内寄送（寄送成功）
  - 省外寄送（寄送成功）
  -  港澳台地区寄送（寄送成功）
  - 国际寄送（寄送成功）
  - 西藏、新疆等偏远地区寄送（寄送成功）
  - 江浙沪包邮区寄送（寄送成功）
  - 疫情地区无法寄送（寄送失败）
- 物品类型：
  - 液体/电子产品/粉尘类，只能选择路运，空运会报错（寄送失败）
  - 管制物品给出提示（寄送失败）
- 重量（首重5kg为15元，每增加1kg增加3元；达到20kg，每增加1kg增加6元）：
  - 物品重量小于5kg，按照首重计价（寄送成功）
  - 物品重量等于5kg，按照首重计价（寄送成功）
  - 物品重量等于5.5kg，按照首重+增重计价，为18元（寄送成功）
  - 物品重量等于6kg，按照首重+增重计价，为18元（寄送成功）
  - 物品重量等于19kg，按照首重+增重计价，为57元（寄送成功）
  - 物品重量等于20kg，按照首重+增重计价，为60元（寄送成功）
  - 物品重量等于20.5kg，按照首重+增重计价，为66元（寄送成功）
  - 物品重量等于21kg，按照首重+增重计价，为66元（寄送成功）
  - 物品重量等于100kg，按照首重+增重计价，为xxx元（寄送成功）
- 体积（首体积为10立方为15元，每增加3个立方增加，3元；达到20立方，每增加3立方增加6元）
  - 同重量测试点（寄送成功）
- 保价
  - 保价，计费为运费+保价（寄送成功）
  - 不保价，计费为运费（寄送成功）
- 运输方式：
  - 当日送达：（寄送成功）
  - 次日送达：（寄送成功）
  - 3日内送达（寄送成功）
- 付款方式：
  - 到付（寄送成功）
  - 寄付（寄送成功）
- 收件人的**地址**/姓名/手机号/身份证号
  - 长度（最大最小）
  - 手机号（11位/非11位）
  - 姓名（中文/非中文）
  - 身份证号（匹配/不匹配/长度不够）
